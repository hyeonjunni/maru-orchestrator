# MARU 엔지니어링 포트폴리오

[English](PORTFOLIO_SUMMARY.md)

MARU는 LLM 에이전트의 작업을 구조화된 산출물, 결정론적 검사, SQLite 상태 기록과 사람의 승인으로 연결하는 로컬 개발 CLI다. 계획자·구현자·리뷰어 사이에서 요청을 복사하고 결과를 전달하던 작업을 자동화하면서 각 단계의 판단 근거를 남긴다. AI의 도움을 받아 개발한 프로젝트이며, 아래 사례는 저장소 감사와 재현 테스트에서 확인한 문제를 다룬다. 실제 운영 장애나 측정하지 않은 사업 성과를 주장하지 않는다.

## 검증 범위

안정화 기준 버전의 Windows 검증 결과는 **283개 통과, 1개 건너뜀**이다. 이 수치는 이전 검증 근거이며 새 공개 후보의 실행 결과가 아니다. 현재 후보의 명령, 결과, 설치 검증과 플랫폼별 한계는 [VERIFICATION_REPORT.md](VERIFICATION_REPORT.md)를 기준으로 한다. 테스트에는 임시 Git 저장소와 기록 기반 또는 가짜 어댑터를 사용했다. 이후 승인된 개인 Claude CLI로 계산기 버그 수정 작업을 실제 실행했다. MARU가 네 역할을 호출해 소스 한 줄을 고쳤고, pytest가 실패에서 통과로 바뀌었다. 51.30초 후 사람의 승인 대기에 도달했으며, 같은 제공자를 사용했으므로 독립 리뷰 완료로 보지 않았다. 일반적인 모델 품질, 생산성 향상이나 비용 절감은 측정하지 않았다.

저장소에는 이미 0.2.0의 컨텍스트·승인 관리 기능이 포함돼 있다. 안정화 작업에서는 이를 보존하고 Core·Relay·State·CLI의 기존 동작을 수정했다. 학습 에이전트, 작업 의존성 스케줄러, 메모리 통합과 대시보드는 미구현 범위다.

## 1. 재실행·재개 경로의 승인 우회 차단

**문제.** 사람의 결정을 기다리는 Arc도 `run` 또는 `resume`으로 다시 계획 단계에 진입할 수 있었다.

**원인.** 재실행 코드는 종료 상태만 검사했고, 재개 코드는 PAUSED 여부만 검사했다. 승인 게이트가 열려 있는지는 확인하지 않았다.

**기술적 결정.** 실행 진입점 두 곳에서 미결 승인 여부를 확인하고, 에이전트 호출이나 상태 전이 전에 중단하도록 했다. 승인 상태는 영속 저장소에서 판단한다.

**구현.** [relay.py](../src/maru/core/relay.py)의 `_restore_or_create_arc`가 열린 게이트를 거부한다. [sqlite.py](../src/maru/storage/sqlite.py)의 `resume_arc`는 `BEGIN IMMEDIATE` 트랜잭션 안에서 게이트를 조회한 뒤 상태를 전이한다. CLI는 거부 사유를 출력한다.

**검증 근거.** [test_relay_restarts.py](../tests/integration/test_relay_restarts.py)는 PAUSED·HUMAN_APPROVAL 상태에서 재실행을 거부하고 에이전트 호출과 이벤트 변경이 없음을 검사한다. 같은 파일에서 재개 거부를, [test_gate_lifecycle.py](../tests/unit/test_gate_lifecycle.py)에서 승인 후 재개를 검증한다.

**절충과 한계.** 승인이 끝나기 전에는 작업이 진행되지 않는다. 권한 관련 차단을 승인해도 구현 완료로 처리하지 않으며 Git 병합도 실행하지 않는다.

**배운 점.** 승인 조건은 정상 실행뿐 아니라 재시도와 복구 진입점에도 적용해야 한다.

## 2. 공유 작업 디렉터리에 맞춘 동시 실행 제어

**문제.** 두 릴레이 프로세스가 같은 소스 파일과 내부 diff 인덱스를 동시에 변경할 수 있었다.

**원인.** SQLite는 개별 갱신을 직렬화하지만, 에이전트 실행과 파일 변경은 여러 트랜잭션에 걸친다. DB 트랜잭션만으로 프로젝트 실행 전체를 보호할 수 없었다.

**기술적 결정.** 설정된 프로젝트 상태 디렉터리마다 릴레이 하나만 실행하도록 OS 파일 잠금을 사용했다. 잠금 충돌은 즉시 알리며 별도의 대기열이나 분산 임대 기능은 추가하지 않았다.

**구현.** [relay.py](../src/maru/core/relay.py)의 `project_lock`은 Windows에서 `msvcrt.locking`, POSIX에서 `fcntl.flock`을 사용한다. `start_run`과 `run_relay`가 각각 잠금을 획득한다. 예외가 발생해도 컨텍스트 관리자에서 해제하며, 잠금 파일의 존재만으로 소유권을 판단하지 않는다.

**검증 근거.** `test_project_lock_rejects_other_process_and_releases_on_error`는 별도 Python 프로세스를 실행해 요청 생성 전 경쟁 실행이 거부되는지 확인한다. 예외로 잠금을 해제한 뒤에는 새 요청 생성이 성공해야 한다.

**절충과 한계.** 같은 프로젝트의 독립적인 Arc도 순차 실행한다. 로컬 프로세스를 위한 제어이며 네트워크 파일시스템과 분산 실행은 검증하지 않았다. 실행 중 설정이 유지돼야 한다. Windows 검증만으로 POSIX 실행 성공을 판단하지 않는다.

**배운 점.** 잠금 범위는 갱신할 DB 행뿐 아니라 실제로 공유하는 작업 디렉터리를 포함해야 한다.

## 3. 재실행 시 요청과 실행 증거 보존

**문제.** 같은 slug로 실행하면 종료 상태를 검사하기 전에 원래 요청을 덮어쓸 수 있었다. 재시작 때 초기화된 단계 번호도 이전 프롬프트와 로그의 파일명을 재사용했다.

**원인.** 요청 저장이 수명주기 검사보다 먼저 실행됐고, 산출물 번호는 프로세스 내부 변수에만 저장됐다.

**기술적 결정.** 동일한 요청의 재사용은 허용하고 다른 요청에는 새 slug를 요구했다. 실행 증거의 번호는 기존 파일 다음부터 부여한다.

**구현.** `start_run`은 기존 요청과 입력 내용을 비교한 뒤 쓰기 여부를 결정한다. 릴레이는 기존 단계·리뷰 번호를 읽어 프롬프트, 스키마, 이력, 테스트 로그의 다음 경로를 정한다. `DIFF_CAPTURED` 이벤트는 최신 diff 파일 대신 번호가 붙은 `full.diff`를 참조한다.

**검증 근거.** [test_relay_restarts.py](../tests/integration/test_relay_restarts.py)의 `test_request_reuse_preserves_original_bytes`는 다른 요청으로 재사용을 시도한 뒤 원본 바이트를 비교한다. `test_restart_preserves_numbered_evidence`는 실패하는 릴레이를 두 번 실행하고 첫 실행의 번호별 파일이 유지되는지, 후속 로그에 두 번째 결과가 기록되는지 검사한다.

**절충과 한계.** 이력 보존에는 디스크 공간이 필요하다. 최신 결과를 가리키는 편의 파일과 사람용 요약은 갱신된다. DB와 파일은 하나의 원자적 트랜잭션으로 저장되지 않으며, 이력의 수동 삭제와 갑작스러운 종료는 정상 재실행 보존 범위에 포함하지 않는다.

**배운 점.** 이벤트를 추가 전용으로 저장해도 참조 파일이 바뀌면 증거가 사라진다. 상태와 함께 산출물의 식별자도 보존해야 한다.

## 4. 구현이 지원하는 복구 범위 정의

**문제.** 중단된 작업에는 복원할 상태와 중단 이유가 필요하다. 동시에 `resume`이라는 이름은 중단된 에이전트 단계부터 정확히 이어 실행한다는 기대를 만들 수 있다.

**원인.** 모델 세션, Arc 상태와 소스 변경의 수명이 서로 다르다. 이를 하나의 복구 가능한 연산으로 취급할 수 없다.

**기술적 결정.** 상태 전이와 승인 결정을 트랜잭션으로 기록하고 실행 증거를 남겼다. 중단 후 소스 변경을 자동 폐기하거나 승인하는 대신 작업 트리 검사와 명시적인 재시작 동작을 유지했다.

**구현.** [sqlite.py](../src/maru/storage/sqlite.py)는 상태 변경과 이벤트를 함께 기록한다. `resume_arc`는 PAUSED 진입 이벤트를 조회해 직전 상태로 되돌린다. 이후 릴레이 실행은 같은 Arc로 계획을 다시 시작한다.

**검증 근거.** [test_core_storage.py](../tests/unit/test_core_storage.py)는 일시정지 전 상태 복원을 검사한다. [test_external_project.py](../tests/integration/test_external_project.py)의 `test_a_paused_relay_resumes_and_never_creates_a_second_arc`는 입력 누락으로 중단한 뒤 복구·재실행해도 Arc가 하나임을 검사한다. 기존 사용자 소스 변경을 보존하는 테스트도 포함돼 있다.

**절충과 한계.** Worker가 소스를 수정한 뒤 중단되면 사용자가 변경을 정리해야 할 수 있다. 에이전트의 정확히 한 번 실행과 DB·파일의 원자적 복구는 구현하지 않았다.

**배운 점.** 복구를 설명할 때는 복원하는 단위를 명시해야 한다. 현재 지원하는 것은 상태와 증거이며 정확한 체크포인트 실행 재개에는 별도 설계와 장애 검증이 필요하다.

## 5. 결정론적 Core와 LLM 판단의 분리

**문제.** 모델의 그럴듯한 응답만으로 상태 전이의 적합성이나 구현 성공을 판단할 수 없다.

**원인.** 모델 출력은 형식이 잘못되거나 내용이 모순될 수 있다. 출력이 실행 권한까지 직접 결정하면 실패 조건을 재현하기도 어렵다.

**기술적 결정.** 전이 규칙, 재시도 한도, 테스트와 승인은 Python에서 제어한다. Planner·Challenger·Worker·Reviewer는 검증된 산출물로 연결한다.

**구현.** [state_machine.py](../src/maru/core/state_machine.py)는 허용된 전이를, [models.py](../src/maru/core/models.py)는 Pydantic 계약을 정의한다. 릴레이는 결과를 검증하고 차단 유형을 분류한 뒤 [testgate.py](../src/maru/core/testgate.py)에서 설정된 argv 명령을 실행한다. 역할별 컨텍스트는 필요한 부분을 선택해 전달하며 대화 전체를 합치지 않는다. 리뷰 통과에도 결정론적 검사의 성공이 필요하다.

**검증 근거.** [test_harness.py](../tests/integration/test_harness.py)는 잘못된 산출물, 모순된 리뷰와 수정 횟수 한도를 검사한다. [test_test_gate.py](../tests/unit/test_test_gate.py)는 명령 순서, 실패 전파와 검사 미설정 시 거부를 검증한다.

**절충과 한계.** 계약과 설정된 검사의 준수 여부를 검증하며 모든 계획의 타당성을 보장하지 않는다. 실행 후 Worker 검사는 OS 격리나 완전한 롤백을 제공하지 않는다. 현재 어댑터는 토큰 수를 채우지 않으므로 프롬프트 바이트 통계를 비용 절감 수치로 해석할 수 없다.

**배운 점.** 모델 판단을 활용하면서도 실행 권한과 실패 조건은 명시적인 규칙으로 유지할 수 있다.

## 6. 테스트와 정적 분석의 검증 역할 구분

**문제.** 기존 성공 경로 테스트로는 승인 우회, 이력 덮어쓰기와 문서에 나온 부분 설정 오류를 발견하지 못했다.

**원인.** 정상 실행과 인터페이스 존재 여부만으로 재시도 경계와 잘못된 입력의 동작을 설명할 수 없었다. 타입 검사와 린트도 이러한 실행 조건을 증명하지 못한다.

**기술적 결정.** 결함을 재현하는 회귀 테스트를 추가하고 구현 중에는 변경 범위만 검사한 뒤 최종 전체 검증을 수행했다. 실제 모델 호출과 오프라인 검증 근거를 구분했다.

**구현.** Pytest 픽스처가 임시 저장소와 가짜 하위 프로세스를 만든다. 설정 테스트는 위험한 경로와 민감한 값을 노출하지 않는 오류 메시지를 검사한다. Ruff와 strict Mypy는 코드 규칙과 타입을 검사한다. [CI 설정](../.github/workflows/ci.yml)에는 세 운영체제의 설치, CLI 실행, 정적 검사, 빌드와 테스트가 포함되며 외부 액션은 SHA로 고정돼 있다.

**검증 근거.** 안정화 보고서에는 수정 전 릴레이 회귀 테스트 6개와 CLI·설정 테스트 21개가 실패한 기록이 있다. 이후 Windows 전체 검증은 283개 통과, 심볼릭 링크 권한으로 1개 건너뜀을 기록했다. 새 공개 후보의 결과는 [VERIFICATION_REPORT.md](VERIFICATION_REPORT.md)에서 관리한다.

**절충과 한계.** 가짜 어댑터는 비용 없이 실패 조건을 재현하지만 실제 인증이나 모델 품질을 검증하지 않는다. CI 행렬이 설정돼 있다는 사실과 원격 실행 통과는 별개의 근거다.

**배운 점.** 동작 테스트, 타입 분석, 설치 후 실행과 원격 CI는 각각 다른 질문에 답한다. 주장에 맞는 검증 결과를 제시해야 한다.

## 7. 설치와 CLI 예제를 실행 가능한 인터페이스로 검증

**문제.** 문서대로 테스트 명령만 설정하면 필수 에이전트 설정 누락으로 실패했다. 개발용 설치에서 동작해도 배포 패키지에 자산이 포함되는지는 별도 확인이 필요했다.

**원인.** 문서의 예제, 설정 기본값과 설치된 배포본을 함께 검증하지 않았다. 설정 파싱 오류와 도구 버전 조회의 시간 초과도 CLI 밖으로 예외를 전달했다.

**기술적 결정.** 기존 명령과 빌드 도구를 유지하고 기본 역할 설정과 사용자가 조치할 수 있는 오류를 제공했다. 소스 체크아웃 밖에서 wheel을 설치해 실행했다.

**구현.** [config.py](../src/maru/core/config.py)는 빠진 역할에 기본값을 적용하고 저장 경로가 프로젝트 내부에 있는지 검사한다. [app.py](../src/maru/cli/app.py)는 설정 실패를 종료 코드 2로 처리하고 버전 조회 시간 초과를 알린다. [pyproject.toml](../pyproject.toml)은 `maru` 진입점과 Hatchling 빌드를 정의하며 프롬프트·스키마는 패키지 내부에 둔다.

**검증 근거.** [test_config.py](../tests/unit/test_config.py)는 부분 TOML 설정을 검사한다. 안정화 보고서는 새 환경에 wheel을 설치한 뒤 체크아웃 외부에서 help·init·status·doctor·잘못된 설정을 실행한 결과와 프롬프트 4개·스키마 4개의 포함 여부를 기록했다. 현재 후보의 설치 결과는 [VERIFICATION_REPORT.md](VERIFICATION_REPORT.md)를 따른다.

**절충과 한계.** Python 3.12 이상이 필요하며 실제 모델 실행에는 외부 에이전트 CLI가 필요하다. 일부 어댑터·헌장 경로가 사용자 지정 `state_dir`을 따르지 않으므로 기본 `.maru` 경로를 권장한다.

**배운 점.** README 명령도 제품의 계약이다. 외부 사용자의 설치 조건에서 직접 실행해야 한다.
